# Task Tracker Architecture

## System overview

Task Tracker is a learning-project application comprising a FastAPI REST API and a self-contained browser-based Kanban client. The API supports creating, retrieving, listing, partially updating, and deleting tasks; list requests can filter by status, priority, overdue state, and tag. Tasks are held in memory and are lost when the backend process restarts.

## Data model

The primary entity is `Task`, represented through three Pydantic models:

- `TaskCreate` defines the fields accepted when a task is created.
- `TaskUpdate` defines optional editable fields for partial updates.
- `TaskResponse` represents the complete stored task, including its ID and timestamps.

A task contains:

- `id`: UUID4 string generated by the storage layer.
- `title`: Required, trimmed, nonblank, and limited to 200 characters.
- `description`: Text that defaults to an empty string.
- `status`: `ToDo`, `InProgress`, or `Done`; defaults to `ToDo`.
- `priority`: `Low`, `Medium`, or `High`; defaults to `Medium`.
- `assignee`: Optional string.
- `due_date`: Optional date.
- `tags`: Trimmed, nonblank strings deduplicated case-insensitively while preserving the first spelling; defaults to an empty list.
- `created_at` and `updated_at`: UTC timestamps managed by the storage layer.

## Create-task request flow

1. A client sends task data to `POST /tasks`.
2. FastAPI receives the request in `app/main.py` and parses it as `TaskCreate`.
3. Pydantic validates and normalizes the submitted fields, rejecting unknown fields and invalid values.
4. The route calls the storage layer, which generates a UUID4 ID and UTC timestamps, constructs a `TaskResponse`, and stores it in a module-level dictionary keyed by task ID.
5. FastAPI serializes the task and returns HTTP 201. Request-validation failures produce HTTP 422.

## Key files

- `app/main.py` — Configures the FastAPI application and CORS middleware and defines the health and task endpoints.
- `app/models.py` — Defines task request and response models, enums, defaults, and validation.
- `app/storage.py` — Implements the in-memory task store and task creation, lookup, filtering, update, and deletion operations.
- `app/business_rules.py` — Implements allowed status transitions, overdue detection, and normalized tag matching.
- `frontend/index.html` — Contains the self-contained Kanban interface and backend API communication.
- `requirements.txt` — Records the Python dependencies.
- `Dockerfile` — Defines the Python 3.11 API image.
- `tests/test_tasks.py` — Covers API CRUD behavior, filtering, validation, and business rules.
- `tests/conftest.py` — Provides shared pytest setup and fixtures.
- `tests/verify_a.py` — Manually verifies model and validation behavior.
- `README.md` — Documents the project and supported local workflows.

## Conventions and business rules

- **Validation:** Unknown fields are rejected. Titles and tags are trimmed, and blank values are rejected where required.
- **Workflow:** Valid status transitions are `ToDo` → `InProgress`, `InProgress` → `Done`, and `Done` → `InProgress`. Invalid and same-status transitions are rejected with HTTP 422 when transition validation is reached.
- **Storage:** Tasks are stored in a module-level Python dictionary without durable persistence. IDs are UUID4 strings, and timestamps use UTC.
- **Updates:** Partial updates apply only explicitly supplied fields. An empty update leaves the task and timestamp unchanged; an explicitly supplied null due date clears the existing due date.
- **Filtering:** Multiple list filters use AND behavior. Tag matching is trimmed, case-insensitive, and exact rather than substring-based.
- **Overdue tasks:** A task is overdue when its due date is before the current local date and its status is not `Done`. A task due today is not overdue.
- **Errors:** Missing tasks return HTTP 404. Request validation and invalid status transitions return HTTP 422. Successful deletion returns HTTP 204.
- **Client/API interaction:** The included browser client communicates with the API at `http://localhost:8000`. The documented CORS configuration permits every origin.

## Limits and unconfirmed areas

The documented architecture confirms process-local storage without durable persistence. Authentication, authorization, deployment infrastructure, a frontend build system, and linting or formatting tools are not established by this document. The `app/api/`, `app/repositories/`, and `app/services/` packages are described as placeholders, not implemented architectural layers. Runtime behavior and test outcomes were not verified for this document.

# Context Engineering Reflection

## Strategy comparison

| Strategy | What it got right | What it got wrong, missed, or invented | Best-suited task shape |
| --- | --- | --- | --- |
| **A — Minimal context** | Produced the broadest narrative, covering the model, request flow, business rules, client interaction, storage limits, placeholder packages, and HTTP behavior. | Made specific claims about client refresh behavior, test fixtures, runtime dependency pinning, and the Docker execution user without identifying their evidence. | Low-risk exploratory drafts that will receive a separate evidence check. |
| **B — Structured context** | Balanced coverage and restraint across the API, client, model, storage, filters, business rules, and placeholder packages while qualifying important unknowns. | Described the client refresh strategy despite later saying it was not established, and gave some test-fixture details more precisely than the stated evidence supported. | Repository-wide architecture documentation, onboarding material, and governance reviews. |
| **C — Targeted context** | Kept the clearest evidence boundary for the create-task flow, Pydantic models, validation, and PATCH behavior. | Its anchor set was too narrow to support a complete repository-level account of the client, business rules, dependencies, tests, startup, and persistence. | Focused component explanations, request tracing, and bounded code reviews. |

## Verdict

I chose **Strategy B, structured context**, because it best balanced repository-wide coverage with explicit evidence boundaries. Strategy A included insufficiently qualified claims, while Strategy C did not cover enough of the system for an architecture overview.

## Reusable rule

For repository-wide architecture documentation, I use **structured context** because repository guidance and file summaries provide broad, traceable coverage. For bounded request-flow or component analysis, I use **targeted context** because anchor files improve precision and expose evidence gaps.
