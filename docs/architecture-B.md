# Task Tracker Architecture

## What the App Does

Task Tracker is a learning-project application for managing tasks through a browser-based Kanban interface and a FastAPI REST API. Users can create, retrieve, list, partially update, and delete tasks. Tasks can be filtered by status, priority, overdue state, and tag. Data is held in memory and is lost whenever the backend process restarts.

## Data Model

The primary entity is a **Task**, with these important fields:

- `id`: UUID4 string generated by the storage layer.
- `title`: Required, trimmed, non-blank, and limited to 200 characters.
- `description`: Optional content; defaults to an empty string.
- `status`: `ToDo`, `InProgress`, or `Done`; defaults to `ToDo`.
- `priority`: `Low`, `Medium`, or `High`; defaults to `Medium`.
- `assignee`: Optional assignee value.
- `due_date`: Optional date used to determine whether a task is overdue.
- `tags`: A list of trimmed, non-blank, case-insensitively deduplicated tags.
- `created_at` and `updated_at`: UTC timestamps managed by the storage layer.

## Request Flow: Creating a Task

1. The user enters task information in `frontend/index.html`.
2. Frontend JavaScript sends a request to `POST /tasks`.
3. FastAPI receives the request in `app/main.py`.
4. A Pydantic model from `app/models.py` validates and normalizes the submitted fields.
5. The route calls `app/storage.py`, which generates the task ID and timestamps and stores the task in a module-level dictionary.
6. The API serializes the created task and returns it to the frontend.
7. The frontend updates the Kanban interface using the API response.

## Key Files

- `app/main.py` — Configures the FastAPI application and middleware and defines all health and task API endpoints.
- `app/models.py` — Defines task request and response models, enums, defaults, and field validation.
- `app/storage.py` — Implements the in-memory task store and task CRUD and filtering helpers.
- `app/business_rules.py` — Enforces allowed status transitions and supports task-related business rules.
- `frontend/index.html` — Contains the Kanban UI, styling, browser interactions, and backend API communication.
- `tests/test_tasks.py` — Tests API CRUD behavior, filtering, validation, and business rules.
- `tests/conftest.py` — Supplies shared pytest fixtures, clean storage, and a test client.
- `tests/verify_a.py` — Manually verifies model and validation behavior.
- `README.md` — Documents the project and supported local workflows.
- `requirements.txt` — Records the confirmed Python dependencies.

## Conventions

- **Validation:** Pydantic models validate requests and responses. Unknown fields are rejected, titles and tags are normalized, and partial updates apply only explicitly supplied fields.
- **Workflow:** Valid status transitions are `ToDo` → `InProgress`, `InProgress` → `Done`, and `Done` → `InProgress`. Invalid and same-status transitions are rejected with HTTP 422 when transition validation is reached.
- **Storage:** Tasks are stored in a module-level Python dictionary without durable persistence.
- **Errors:** FastAPI/Pydantic handles request-validation failures; invalid status transitions use HTTP 422. Other error-response details are not confirmed by the supplied context.
- **Frontend/backend interaction:** The self-contained frontend communicates with the API at `http://localhost:8000`. CORS currently permits every origin.
- **Filtering:** Multiple list filters use AND behavior. Tag matching is trimmed, case-insensitive, and exact rather than substring-based.
- **Overdue tasks:** A task is overdue when its due date is before the current local date and its status is not `Done`; a task due today is not overdue.
